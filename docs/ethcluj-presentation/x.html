The Problem: at projected rate, state will grow into the terabytes zone, in just a few years
resource: ethpandaops - TheLab: EL world state growth

ZKEVMs solve verification.
But who will hold the state?

  • ZKEVMs decouple verification from state — validators no longer need full state to verify blocks. A single SNARK proof replaces re-execution entirely.
  • No reason to even hold state — today, nodes hold Ethereum's 300+ GB state as a byproduct of block verification. Once ZKEVMs remove that need, there's no incentive to keep it at all.
  • Centralization trap — only RPC providers and block builders will retain state, creating de-facto data centralization. Running Full Nodes will be the exception, rather than the rule.
  • The mempool problem — without state, nodes can't validate transactions, undermining censorship resistance mechanisms like FOCIL.

Core Concept of Partial Statefulness

What if nodes could hold only
what they care about...

EL logical state topology: MPT traversal → implicit key-addressed trie. Partial Nodes would need a minimal data-set for coherence.

  • Full account trie — every account's balance, nonce, and code hash is synced. The complete view of all 300+ million accounts.
  • Selective storage — only download storage and bytecode state sub-graphs for contracts you choose to track (e.g., WETH, DAI, Uniswap).
CL logical state topology: SSZ container → explicit tree. Partial Nodes would NOT need a minimal data-set for coherence.

  • State sub-graphs — partial nodes can keep just the CL state sub-graphs that are of interest to them.

...and still be coherent
under the canonical state root?

No re-execution: a small, widely available data set updated via some vehicle, e.g. Block Access Lists (BAL), keeps everyone coherent.

03 / 09
No Re-Execution

Following the tip of the chain with Full-state diffs + Account-hash diffs

  • 1. Snap sync account trie — download all accounts + intermediate MPT nodes (~50 GB).
  • 2. Snap sync tracked storage — download full storage tries for selected contracts.
  • 3. Heal state — apply state diffs per block, then hash everything up to state root and compare it with the block header root.

For coherence, Partially Stateful (PS) nodes need: balance changes, nonce changes, storage writes, code changes — per account. Tracked contracts need full storage updates. For untracked contracts, the node needs to check which ones changed and update their account-level hash.

Resolving untracked contracts: Ideally, the vehicle carrying the full-state diffs would include account-hash diffs for all accounts touched by the current block's transactions — making partial nodes self-sufficient.

post-Glamsterdam BAL change proposal

Add account-hash diffs to Block Access Lists

BAL contains: balance changes, nonce changes, storage writes, code changes — per account, per transaction.

Proposal: Add block hash diffs as a list of the addresses touched by the block accompanied by the account's pre-state hash and its post-state hash. This unlocks P.S. and VOPS (with ZKEVM).

Design Space

Domain-Separated State Subgraphs EL and CL

Currently, Beacon DB ~100 - 200 GB; TBD the size in zk Nodes, probably depending on Weak Subjectivity Period and reorg window.

  • EL existing topology: Accounts, Storage
  • CL existing topology: Validator registry & Balances, Randomness & Slashings, [...], History, Participation & Inactivity, Finality

zk Stateless nodes: No EL or CL state - Attesting nodes

zk Partial nodes: Extend Partial Statefulness to CL by leveraging this "state as a partially divisible graph".

Capabilities: No re-execution; Attesting; Participating in Censorship Resistance schemes (FOCIL); RPC calls, Queries & State serving (for tracked accounts, contracts & domains).
