Why This Matters

ZK makes verification cheap.
State serving may centralize.

Verification plane

Future zk nodes can attest without holding full EL state.

State plane

Builders, RPCs and indexers still need state to build, serve, and answer queries.

Risk: Ethereum verification decentralizes while authenticated state access collapses into a small state-serving class.

The mempool problem: without state, nodes cannot validate transactions locally, weakening censorship-resistance mechanisms like FOCIL.

Goal: Partial Clients should verify both application state and consensus facts without trusting centralized EL or beacon RPCs.

Core Concept of Partial Statefulness

What if nodes could hold only
what they care about...

EL logical topology: MPT traversal → implicit address-keyed trie. Partial Nodes need a coherence dataset (account-level hashes) plus local MPT corridors.

  • Account commitments — maintain accountHash values for relevant or broad account ranges.
  • Selective storage/code — keep contract State Sub-Graphs for contracts the node chooses to track.
CL logical topology: SSZ BeaconState container → explicit top-level field roots. Partial Nodes can track selected CL State Sub-Graphs.

  • Coordination facts — validators, balances, finality, slashings/exits/withdrawals, and execution-payload bridge data.

under canonical roots?

Functional domains: Both the EL and the CL state graphs, albeit very different in structure, admit a topological decomposition along functional boundaries, and although their topology is already organized along functional domains, this property remains currently unexplored.

Architecture Split

Three planes.

EL · validity

Execution correctness proven by zk; most nodes need not store full EL state.

CL · coordination

Fork-choice, finality, validator lifecycle, payload anchoring.

State · service

Selective persistence, authenticated RPC, proof serving, slice healing.

Partial Statefulness lives mainly in the state-service plane: make selective state useful enough to be widely held.
04 / 11
The Partial Node

ZK makes stateless validators real.
Partial Nodes make state useful again.

  • Old model: validating implied re-execution; re-execution implied full state.
  • ZK model: validators can verify proofs without holding full EL state.
  • Adoption upside: VOPS enables “Ethereum on toasters” — tiny zk-verifying nodes for browsers, phones, embedded devices, and low-power machines.
  • Protocol risk: if nobody needs state to verify, state serving drifts toward builders, provers, and centralized RPCs.
  • Partial Statefulness: introduces a middle tier that keeps selected state useful, coherent, and proof-serving.
ZK-era state-retention classes 0. Light Client └─ headers / finality / remote state 1. Partial Node / Partial Client ├─ VOPS │ validity-only partial statelessness │ zk attesting + CR / FOCIL │ minimal local state, no general RPC serving │ ├─ Wallet / App Partial Client │ selected EL + CL state │ local verified reads │ ├─ Edge Partial Node │ selected State Sub-Graphs │ MPT + SSZ corridors │ authenticated local RPC │ └─ State Mesh Node many state bundles proof serving / state markets 2. Full Node ─ full current EL+CL state 3. Archive Node ─ full node + historical state

Key point: VOPS are a subset of Partial Nodes — the smallest Partial Node profile: validity-only, nearly stateless, optimized for mass adoption.
